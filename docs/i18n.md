# i18n

The UI supports English (the default) and Ukrainian, selected via the
`LOCALE` environment variable.

## Why `LOCALE` and not `NEXT_PUBLIC_LOCALE`

Next.js inlines every `NEXT_PUBLIC_*` variable into the client JavaScript
bundle **at `next build` time**. Under this project's deploy model — build
one image, run it in many places/configurations — that would mean baking a
language choice into the image itself, forcing a rebuild any time you wanted
to change it.

Instead, `LOCALE` is a plain server-only env var (see
[`apps/nextjs/src/env.ts`](../apps/nextjs/src/env.ts)):

```ts
LOCALE: z.enum(["en", "uk"]).default("en"),
```

The root layout is a **server component**, so it can read `env.LOCALE` fresh
on every request/boot and pass it down as a prop to
[`AppConfigProvider`](../apps/nextjs/src/components/app/AppConfigProvider.tsx),
a client component that wires it into `react-i18next` for the rest of the
tree:

```tsx
export function AppConfigProvider({ locale, supportUrl, children }: AppConfig & { children: React.ReactNode }) {
  const i18n = useMemo(() => getI18n(locale), [locale]);
  ...
  return (
    <AppConfigContext.Provider value={config}>
      <I18nextProvider i18n={i18n}>{children}</I18nextProvider>
    </AppConfigContext.Provider>
  );
}
```

Because the value is read at request/boot time rather than baked into the
bundle, **changing `LOCALE` only needs a container restart** (`docker compose
up -d` picks up the new `.env` value) — not a rebuild. `SUPPORT_URL` (the
optional Settings/Profile support link) is threaded through the exact same
way, for the same reason.

Client components read the active locale via `useAppConfig()` (for
`locale`/`supportUrl` directly) or the normal `useTranslation()` hook from
`react-i18next` (for translated strings, with full interpolation/pluralization
support). Server-only code that never renders as a React client component
(route handlers, `generateMetadata`, plain server modules) uses the small
`getMessage(locale, key)` helper in
[`apps/nextjs/src/lib/i18n/index.ts`](../apps/nextjs/src/lib/i18n/index.ts)
instead, which falls back to English for any missing key.

## Adding a third language

1. Add a new messages file, e.g. `apps/nextjs/src/lib/i18n/messages/de.json`,
   mirroring the shape of `en.json`.
2. Register it in the `MESSAGES` map and `SUPPORTED_LOCALES` in
   [`apps/nextjs/src/lib/i18n/index.ts`](../apps/nextjs/src/lib/i18n/index.ts):
   ```ts
   import de from "./messages/de.json";
   export type Locale = "en" | "uk" | "de";
   export const SUPPORTED_LOCALES: readonly Locale[] = ["en", "uk", "de"];
   export const MESSAGES: Record<Locale, Record<string, unknown>> = { en, uk, de };
   ```
3. Add the new value to the `LOCALE` zod enum in
   [`apps/nextjs/src/env.ts`](../apps/nextjs/src/env.ts):
   ```ts
   LOCALE: z.enum(["en", "uk", "de"]).default("en"),
   ```
4. Set `LOCALE=de` in `.env` and restart the `web` container — no rebuild
   needed.
